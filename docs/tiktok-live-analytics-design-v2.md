## ✅ 確定事項（このチャットで合意済み）

| 論点 | 決定内容 |
|---|---|
| 配信環境 | スマホからTikTokアプリで直接配信（OBS等の配信ソフトは未使用） |
| スクショ取得方式 | **方式C**：サーバーPC上のヘッドレスブラウザ(Playwright等)で対象ライブの視聴画面を匿名で開き、開始直後に1枚キャプチャ。将来の複数ライブ同時監視とスケールを揃えるため、当初検討の別端末ADB方式(旧方式B)から変更。ログイン・API操作なしのためBot判定リスクなし。Phase 3冒頭でブラウザ視聴の成立性を先に検証する |
| レポート生成タイミング | **配信終了後にまとめて1本**生成（リアルタイム簡易表示は今回は不要） |
| ダッシュボードの用途 | **常設・事後振り返り用**。配信中にリアルタイム監視する画面ではなく、過去の配信レポート・数値推移をいつでも一覧・参照できるWeb画面 |
| **開発時の実行環境** | **サーバーは使わず、手持ちの常時稼働可能なPC1台で開発・検証を進める**。コスト最小化を優先し、サーバー/IPプール化(5.4節)は本番スケール時の後続フェーズとする |
| **ライバー管理** | `streamers` テーブルを**最初から**用意し、1人運用の段階でも `streamer_id` を全データに紐付ける(将来の複数ライバー対応時の移行コストを避けるため) |
| **レポート生成トリガー** | **自動検知(一定時間イベントが来なければ配信終了とみなす)＋手動実行も可能**の両対応 |
| **生ログの保存方針** | 集計・加工済みデータだけでなく、受信した生JSONも必ず保存する(後からの再分析・仕様変更に耐えるため) |

この決定を踏まえ、以下の設計は上記を前提に記述する。

## 0. スコープの前提（重要）

このツールは以下の範囲で設計する。

| 対象 | 方式 | 状態 |
|---|---|---|
| コメント・ギフト・視聴者数 | 公開ストリーム受信（ログイン不要） | ✅ 実装可能 |
| ショップ/オークション購入者ランキング | ログイン＋署名偽造＋CAPTCHA回避が必要 | ❌ 対象外（前回合意の通り） |
| ライブのスクリーンショット | 後述4パターンから選択 | 要確認 |

購入者ランキングを含めない前提で、「コメント・ギフト・視聴者数の推移」＋「配信の映像(服装・画角)」の2種類の情報から、AIが次回配信への改善提案を出す、という構成にする。

## 2. データ取得層（変更なし・確実に作れる部分）

- 対象: コメント／ギフト／視聴者数／いいね数
- 方式: TikTok公開WebSocket相当のストリームを購読（既存OSSライブラリ、例: `TikTokLive` (Python) を利用）
- ログイン不要・受信専用のため、Bot判定リスクなし。24時間運用も問題なし。
- **開発時の実行環境**: サーバーではなく、手持ちの常時稼働可能なPC1台上でプロセスを稼働させる。コスト最小化を優先し、複数同時監視のためのサーバー/IPプール化(5.4節)は本番スケール時のフェーズとする
- 取得イベント例:
  - `comment`（誰が・いつ・何を書いたか）
  - `gift`（誰が・何を・いくつ・いつ送ったか、コンボ状況）
  - `viewer_count`（一定間隔でのスナップショット）
  - `like`（累計いいね数の推移）
  - `follow` / `share`（新規フォロー・シェアイベント）
  - `room_enter` / `room_leave` (可能な範囲で)
  - `battle_opponent`（PK対戦相手の検知。`Battle`/`LinkMic`/`Armies`系の生イベントから`anchor_info`をパースして対戦相手IDを抽出。ログイン不要・公開イベントの範囲内)

### 配信終了の検知とレポート生成トリガー
- **自動検知**: 一定時間(閾値は実装時に調整。目安30秒〜1分程度)イベントが来なければ「配信終了」とみなし、`live_sessions.status` を更新してレポート生成を自動キック
- **手動トリガーも用意**: 誤検知時や任意のタイミングで再生成したい場合に備え、手動でレポート生成を実行できるコマンド/エンドポイントも用意する
- どちらの経路で終了したかは `end_detection_type` に記録し、後から自動検知の精度を振り返れるようにする

### PC単体運用に伴う注意点(実装で考慮する)
- 自宅回線のIPが変動する可能性があるため、接続断からの自動再接続処理を組み込む
- PCのスリープ設定をオフにし、再起動時にプロセスが自動起動するようにする(OSのタスクスケジューラ/systemd等を利用)

### 常駐監視(配信開始の自動検知) — 実装済み
「いつ配信が始まるか分からない」問題への対応として、登録ライバーを常時監視し、配信開始を自動検知して記録を開始する常駐機能(`watch.py`)を実装済み。
- 監視対象ライバーを複数登録可能。プロセス起動後、一定間隔(既定60秒)で各ライバーのライブ状態をポーリング
- 配信開始を検知したら、既存の記録処理(`SessionRunner`/`run_with_reconnect`)を自動起動。スクショ取得・バトル検知も監視経由でそのまま効く
- 配信終了を検知したら待機に戻り、次の配信開始を待つ(「待機→検知→記録→終了→待機」のサイクル)
- **単一IP制約(5.4節)**: 単一IPでは同時に1配信しか記録できないため、複数ライバーが同時配信中の場合は「登録順で最初に見つかった方を優先」というルール。複数同時記録はPhase 5(複数IP構成)の対象
- レポート生成は自動化せず手動トリガーのまま(APIトークンの消費タイミングを手元で管理するため)
- ライブ状態のポーリング・記録はAIを使わないため、待機中・記録中のAPIトークン消費はゼロ。トークンを消費するのは配信終了後の手動レポート生成時のみ
- 実配信で全4フェーズ(待機/検知→記録/終了検知/待機復帰→再検知)を確認済み

## 3. スクリーンショット取得層（新規）

「服装」「画角」についてAIにコメントさせたいとのことなので、配信映像の静止画を定期取得する層を追加する。

将来的に1サーバーで複数ライブを同時監視する構成(5.4節)を見据え、**方式C: サーバーPC上のブラウザ(ヘッドレス)で対象ライブの視聴画面を開いてキャプチャ**を採用する。当初検討していた「別端末でのADBキャプチャ(方式B)」は、1配信=1端末に近くなり複数ライブ規模で非現実的なため、1サーバー内でスケールできる方式Cに変更した。

### 方式Cの具体設計

- コメント収集システム(Pythonプロセス)と同じサーバー上で、ヘッドレスブラウザ(Playwright等)を使い、対象ライブの視聴画面を匿名(ログインなし)で開く
- 配信開始直後に1枚キャプチャして保存(当初は1配信1枚。撮影タイミング・枚数は後のPhaseで拡張)
- ログイン不要・API呼び出しなし・匿名視聴＋スクリーンショットのみなので、TikTok側の検知システムを経由しない(人間が視聴しながらスクショを撮るのと同じ扱い)
- 画質はブラウザ視聴画面の解像度に依存するが、服装・画角の判定用途には十分

### 重要: Phase 3冒頭で成立性を検証する

TikTok LiveをPCブラウザ(ヘッドレス含む)で開く際、ログインを求められたり視聴画面の表示に制約が出る可能性がある。そのため、Phase 3の最初に「サーバーPCのヘッドレスブラウザで、匿名のまま対象ライブの視聴画面を開いて1枚キャプチャできるか」を小さく検証してから本実装に進む。もしブラウザ視聴に大きな制約(ログイン必須など)が判明した場合は、その時点で別端末ADB方式(旧方式B)を再検討する。

### 運用上の注意点

- 当初は「配信開始直後に1枚」。将来的に複数枚撮る場合は、「中盤」「盛り上がり時間帯(ギフトが多かった時間帯など、第1層のデータと突き合わせて選定)」「終盤」など分析上意味のあるタイミングを狙うと、AI分析での代表サンプルの質が上がる
- 人物が映っていない場合の再撮影機能は後のPhase(6)で対応

## 4. ストレージ設計

### 4.1 テーブル構成（例: PostgreSQL + TimescaleDB、または SQLite for 個人利用・開発時のPC1台運用）

```sql
-- ライバー(配信者)。1人運用の段階でも最初から用意する
streamers (
  id, name, tiktok_account_id, created_at
)

-- ライブ配信そのもの
live_sessions (
  id, streamer_id,  -- streamersへの外部キー。全データがここに紐づく
  title, started_at, ended_at, status,  -- status: live中/終了/エラー中断 など
  end_detection_type  -- auto(自動検知) / manual(手動終了) を記録し、後から誤検知を追跡できるようにする
)

-- 時系列イベント(コメント/ギフト/視聴者数などをまとめて記録)
live_events (
  id, live_session_id, event_type, -- comment/gift/viewer_count/like/follow/share
  user_id, user_nickname,
  payload JSONB,      -- コメント本文、ギフト種別・個数、視聴者数など type別に集計・加工した内容
  raw_payload JSONB,  -- 受信した生JSONをそのまま保存。後からの再分析・仕様変更に対応するため必須
  occurred_at          -- UTCで統一して保存し、表示時にJSTへ変換する
)

-- スクリーンショット
live_screenshots (
  id, live_session_id, captured_at, image_path,
  ai_analysis JSONB  -- 服装/画角などのAI分析結果をキャッシュ
)

-- AI分析レポート(配信ごと)
live_reports (
  id, live_session_id, generated_at,
  summary_json JSONB,      -- 構造化された分析結果
  recommendation_md TEXT   -- 次回配信への提案(フォーマット済みMarkdown)
)
```

- 個人〜小規模運用なら SQLite でも十分。将来的に複数配信者・大量データを扱うならPostgreSQLへ。

## 5. AI分析層（新規・今回の核心）

分析は大きく2種類に分ける。

### 5.1 数値・コメント分析(テキスト系)

入力: `live_events` から集計したデータ
- 時間帯別の視聴者数推移グラフ用データ
- ギフトの発生タイミングと金額規模の推移
- コメントの盛り上がりタイミング(投稿頻度のスパイク検出)
- コメント内容のテーマ分析(何の話題で盛り上がったか／荒れたか)
- 新規フォロー・シェアが増えたタイミングとの相関

処理: 生ログをそのままAIに渡すとトークンを圧迫し、かつノイズが多いと重要なコメントを見落としやすくなる。一方で単純なランダム/先頭150件サンプリングでは網羅性が足りず、重要なコメント(炎上の火種・神リクエスト・盛り上がりのきっかけ)が漏れるリスクがある。そこで**「全件を保持・考慮した上で、AIには凝縮して渡す」2層アプローチ**を採る。

**前提**: コメントは全件が既に`live_events`にraw_payloadごと保存済み(Phase 1)。失われていない。問題は「AIに渡す時の絞り方」だけ。

**層1: 標準レポート = 賢い前処理(全件をコード側で"見て"から凝縮)**
単純サンプリングをやめ、全件を処理してから意味のある形に凝縮してAIに渡す:
- 盛り上がり検出: コメント頻度が急増した時間帯を全件から自動検出し、その前後のコメントを厚めに拾う
- ノイズ除去: 単なる挨拶・スタンプ連打・意味の薄い相槌を除外し、意味のあるコメントの比率を上げる
- カテゴリ別代表抽出: 質問・リクエスト・ネガティブ反応・ギフト関連など、種類ごとに代表を拾い、種類を網羅する
- 時間帯ごとの要約: 数分バケットごとに「この時間帯は何の話題で盛り上がったか」をコード側で粗く集計
→ 全件を考慮しつつ、AIに渡す量は抑えられ、網羅性とコストを両立できる

**層2: 深掘りモード = 対象を絞って全件送り**
「特定の時間帯を徹底分析したい」「この配信は特別なので細かく見たい」時のために、対象を絞って全コメントを送るモードを用意する。範囲を絞れば全件でもトークンは抑えられる(例: 「18:00〜18:30の全コメントを分析」)。

**将来**: 分析の切り口(プロンプト)を差し替え可能にする構想もある(標準/新規ギフター特化/特定時間帯深掘り/トラブル検出 など)。`winning_patterns.md`を切り出したのと同じ発想。採否は後で判断。

出力例:
- 「開始10分は視聴者数が伸び悩んだが、◯◯の話題を振った13分時点から急増」
- 「ギフトは深夜帯より20時台に集中。生活リズムに合わせた開始時刻の検討余地あり」
- 「コメントのネガティブ比率が◯分間だけ上昇。原因は音声トラブルの言及」

### 5.2 スクリーンショット分析(画像系)

入力: `live_screenshots` の画像(配信中、数分おきに数枚〜十数枚を代表サンプルとして選定)

Claude APIの画像入力機能を使い、各スクショについて:
- 画角（顔・上半身の収まり方、余白、傾き、照明）
- 服装(色味・清潔感・配信内容とのマッチ度合いなど、事実ベースの記述にとどめる)
- 背景・照明の一貫性

**注意点(設計上の配慮)**:
- 服装や外見に関するAI分析は、本人が「改善のための客観的フィードバックが欲しい」という明確な目的で使うツールである前提で設計する
- 出力は「良い/悪い」の断定ではなく、「画角がやや左に寄っている」「照明が暗く表情が見えにくい時間帯がある」など、**観察事実＋改善余地**の形にする
- 顔認識や個人の特定・評価を行うものではなく、あくまで配信者自身が自分の配信映像を分析する用途に限定する

### 5.3 統合レポート生成

数値分析＋画像分析の結果を統合し、あらかじめ用意したフォーマットに沿って「次回配信への提案書」を生成する。

**フォーマット例(叩き台。実際は次回チャットで用意されるフォーマットに合わせて調整)**:

```markdown
# 配信分析レポート — 2026/08/24

## サマリー
- 配信時間: 20:00-22:00 / 平均視聴者数: 320人 / 最大: 480人
- 総ギフト: ◯◯pt / コメント数: ◯◯件

## 数値のハイライト
- 視聴者数が最も伸びたのは◯分台。きっかけは〜
- ギフトが集中した時間帯とその文脈

## コメント傾向
- ポジティブ/ネガティブの比率と主なトピック
- よく出た質問・リクエスト

## 映像面のフィードバック(スクショ分析)

```

## 5.4 スケール構成: サーバー・IPアーキテクチャ(複数ライブ同時監視)

### 前提となる制約
TikTokライブの仕様上、**同一IPから複数ライブへ同時接続すると、先に接続していたライブから強制的に切断される**(1IP=1セッション)。そのため、同時監視したいライブ本数と同数のIPが必要になる。

※これは「Bot検知を回避するためのIPマスキング」ではなく、「プラットフォームの技術的仕様(1IP1セッション)に対応するための、必要IP数の確保」という位置付け。ログイン偽装や検知回避を目的とした設計は行わない。

### サーバー規模の目安(層1データ取得のみ・受信専用)
- 1接続あたりの負荷は軽量(JSONイベント受信・パース・DB書き込みのみ)
- 100接続程度であれば、中規模VPS(4vCPU/8GBメモリ相当)1〜2台で計算リソース面は十分。ボトルネックは計算資源ではなく「確保できるIPの数」

### IP調達方法とコスト目安(100ライブ同時監視の場合)

| 調達方法 | 1IPあたり月額目安 | 100IP換算 |
|---|---|---|
| クラウド標準グローバルIP(AWS Elastic IP等) | 約$3.6〜5 | $360〜500/月 |
| VPS事業者の追加IP(Floating IP等) | 約$2〜4 | $200〜400/月 |
| データセンター系IPのブロック購入 | 約$0.5〜1.5 | $50〜150/月 |

サーバー本体費($100〜200/月)＋IP調達費を合わせ、**月額$200〜600程度**が100ライブ同時監視の概算レンジ(事業者・契約形態により変動。本格導入前に複数社から見積もり推奨)。

### IP割り当てアルゴリズム(リソースプール方式)

```
ip_pool (
  ip_address, status,        -- available / in_use
  assigned_live_id, assigned_at
)

割り当てロジック:
1. 新規ライブの監視リクエスト発生
2. status='available'なIPを1つ取得(排他制御)
3. そのIPで接続開始、status='in_use'に更新
4. ライブ終了(終了イベント検知 or 一定時間無通信でタイムアウト)でstatus='available'に戻す
5. 空きIPがない場合はキューで待機
```

設計上の注意点:
- 終了検知の遅延に備え、IPプールは監視本数+αで持つ(例: 100本監視なら110IP程度)
- サーバーごとにIPを固定グループ分けしておくと運用がシンプル(例: サーバーAに1-40番、サーバーBに41-80番)
- **スクショ取得(方式C)もIP分散の対象に含める**: Phase 3の検証中、短時間に同一IPから多数のブラウザアクセスを行った際、TikTok側のWAFで一時的にブロックされる事象を確認した。これはコメント取得側の「1IP=1セッション」制約とは別で、「短時間・同一IPからの大量アクセス」に対するWAFの反応。複数ライブを同時監視する際は、コメント取得だけでなくスクショ取得のブラウザセッションも同じIPプールで分散させ、単一IPからのアクセス集中を避ける必要がある

## 5.5 AI分析のコスト試算（長時間配信）

### 前提: 集計してから渡す設計が効く
現在の実装は設計書5.1の方針どおり「生ログを直接AIに渡さず、コード側で集計・要約してから渡す」形。このため、**配信時間が延びてもAIに渡すデータ量は比例して増えない**。

- 時系列(視聴者数・ギフト・コメント数)は1分バケットで集計 → 4時間でも約240行程度
- コメントは全件でなく代表サンプリングして渡す → 何千件でも渡す量は一定
- サマリー数値はコード計算 → トークン消費なし

### 概算(Claude Sonnet 5、要実測での補正)
| 項目 | 3分配信 | 4時間配信(集計あり) |
|---|---|---|
| 入力トークン | 数千 | 1〜3万程度 |
| 出力トークン(レポート本文) | 千〜数千 | 千〜数千(レポート長は配信時間に依存しない) |
| 1配信あたり概算コスト | 数円 | 十数円〜数十円程度 |

**4時間配信でも1配信あたり数十円程度**の見込み。ただし「集計してから渡す」設計が守られている前提。実装確認事項:
1. コメントを全件でなく代表サンプリングして渡しているか
2. 時系列が1分バケット集計済みか
3. 実際のレポート生成時の `usage`(input/output tokens)をログ出力し、実測値で上記を補正する

複数ライバーを大量に回す場合でも、1配信数十円 × 配信数 で見積もれるため、サーバー・IP費用(月$200〜600)に比べればAI分析コストは相対的に小さい範囲に収まる見込み。

## 5.6 将来構想: 蓄積データの活用（今すぐ作らない・参考）

ライブデータと分析結果が蓄積されていくにつれ、それを分析に活かしたいという要望がある。方向性として2つあり、混同しないことが重要。

### アプローチA: モデルの再学習(ファインチューニング) — 非推奨
モデル自体を貯めたデータで鍛え直す方法。大量データ・コスト・専門知識が必要で、個人〜小規模チーム規模では見合わない。Claude APIでは基本的に提供もされていない。**採用しない。**

### アプローチB: 蓄積データを「文脈」として渡す — 現実的、将来こちらで発展
モデルは変えず、渡す情報を賢くする方法。既に運用している `winning_patterns.md`(勝ちパターンをプロンプトに埋め込む仕組み)がこの入り口。発展させると:
- 過去の配信レポートや、うまくいった配信の特徴を蓄積し、分析時に「参考データ」として渡す
- 「この配信者は過去にこういう傾向があった」という履歴を踏まえた分析
- 追加コストはわずかで、今の設計の延長で実現できる

**今すぐ作るものではない**が、将来はアプローチBの方向で発展させる、と位置づけておく。

## 7. 開発フェーズ案(Claude Codeでの実装順)

1. **Phase 1**: 開発用PC上での環境構築＋データ取得層の実装(単一ライブ、コメント/ギフト/視聴者数をDBに保存するだけ)
2. **Phase 1.5**: バトル相手検知ロジックの追加(`Battle`/`LinkMic`/`Armies`系イベントから`anchor_info`をパースし、`battle_opponent`イベントとして記録)。データ取得の抜け漏れを防ぐため、ダッシュボード構築前に対応する
3. **Phase 2**: 事後振り返り用ダッシュボードの最小版。以下を表示(過去の類似ツールの画面構成＋時系列グラフを統合):
   - ライブ一覧(セッションID・配信開始/終了・総配信時間・最終合計いいね数・最高/平均同接)
   - 時系列グラフ(視聴者数推移・コメント数推移・ギフト(ダイヤ)推移)
   - バトル相手一覧
   - ギフトユーザーランキング(ユーザー名・ギフレベ・ダイヤ合計)
   - ギフト詳細(明細一覧)
   - 入室管理(ユーザー名・ギフレベ・入室回数)
   - フォローユーザー一覧
   - コメント一覧
   AI分析はまだ含めない
4. **Phase 3**: スクリーンショット取得(方式C: サーバーPCのヘッドレスブラウザ、1配信1枚から)。冒頭で「匿名でブラウザ視聴＆キャプチャが成立するか」を小さく検証してから本実装に進む
5. **Phase 4**: AI分析層(数値・コメント分析→配信終了後のレポート自動生成)＋画像分析(服装/画角)の統合
6. **Phase 5**: サーバー・IPプール化による複数ライブ同時監視への拡張(小規模でIP割り当てロジックを検証してから台数を拡大)
7. **Phase 6**: スクショ再撮影機能、複数配信比較機能、レポートフォーマットの微調整

各フェーズごとに動くものを作り、実際のライブで試してから次へ進む形を推奨。
