# ダッシュボード UI設計案（v1）
## 〜 1人の配信をじっくり分析する、本人＋運営チーム向け画面 〜

## 0. 設計の前提（合意事項）

| 論点 | 決定 |
|---|---|
| 方向性 | 既存の最小版に縛られず、ゼロベースで理想形を設計 |
| 利用者 | 配信者本人 ＋ マネージャー/運営チームの両方 |
| 最重視 | **1人の配信をじっくり分析する**こと（複数ライバー一覧は将来対応） |
| デザイン | この段階で本格的に着手（これまでは機能優先でデザイン未着手だった） |

利用者が「本人」と「運営チーム」の両方なので、**専門用語を並べるだけの画面ではなく、本人が見ても示唆が分かる見せ方**を意識する。一方で運営チームが数値を深掘りできる詳細も残す。

### 実データ検証で判明した、実装時に踏まえるべき点（session 9 = 7時間・生誕祭配信）

- **テストデータは session 9 を使う**: 7時間・コメント2,580件・ギフト2,923件・バトル47回・視聴者数10,450スナップショットという濃い実データ。これで本番同様の見え方を確認できる
- **バトルが47回ある**: UI設計案では「バトル区間を背景の帯で表示」としていたが、47回もあると帯だらけで見にくい可能性が高い。実際に session 9 で描画して、帯・マーカー・切替のどれが見やすいか確認して選ぶ
- **長時間のデータ点が多い**: 視聴者数10,450点・7時間分。そのまま全点描画すると重く見にくいので、分単位などに集計・間引いて描画する
- **ギフト集計は修正済みロジックを使う**: TikTokの重複配信・log_id使い回しに対応した集計(`(log_id, streaking, diamond_count, repeat_count)`でグルーピング)。ダッシュボードの`queries.ts`にも適用済み。KPIやグラフはこの修正後の数値を使う
- **大型ギフトの外れ値**: 生誕祭では単発で数万〜20万ダイヤのギフトが入る。ギフトの棒グラフはスケールが大型ギフトに引っ張られて他が潰れないよう、対数スケールや上限設定などの工夫を検討する

## 1. 画面構成（3階層）

```
[L1] ライバー選択 / 配信一覧（入口）
        ↓ 配信を選ぶ
[L2] 配信ダッシュボード（1配信をじっくり分析）★ここが主役
        ↓ さらに深掘り
[L3] 詳細データ（コメント全文・ギフト明細などの生に近いデータ）
```

今回の最重視は **L2（1配信の分析画面）**。ここを最も作り込む。

---

## 2. L2: 配信ダッシュボード（主役画面）の設計

1つの配信を開くと、上から下へ「概要 → AI提案 → 数値の深掘り → 詳細」の流れで読める構成にする。**上に行くほど要約・示唆、下に行くほど生データ**、という情報の階層を作る。

### 2-1. ヘッダー（配信の基本情報）
- 配信者名 / 配信日時（JST）/ 配信時間 / ステータス（配信中・終了・エラー）
- 主要KPIを大きく数枚のカードで: 平均視聴者数・最高同接・総ギフト(ダイヤ)・コメント数・新規フォロー・バトル回数
- **各KPIに「勝ちパターン基準との対比」バッジを付ける**（例: 平均視聴時間が基準1分30秒に対して足りていれば緑、不足なら黄など）。本人が一目で「今回どうだったか」を掴める

### 2-2. AI分析レポート（要約と提案を最上部近くに）
- Phase 4で生成したレポートを表示。特に「次回配信への提案」は本人が最も見たい部分なので目立たせる
- レポート未生成なら「生成する」ボタン（後述のPhase 4仕上げと連動）
- レポートに「勝ちパターン反映済み」バッジを出し、基準に沿った分析であることを明示

### 2-3. 時系列の主役グラフ（1配信の"物語"を見せる）
ここが「じっくり分析」の核。**複数の指標を1つの時間軸に重ねて、配信中に何が起きたかを一望できる**ようにする。

- **メインの複合グラフ**: 横軸=配信経過時間。以下を重ねて表示（表示ON/OFF切替可）
  - 視聴者数（折れ線）
  - ギフト（ダイヤ）発生（棒）
  - コメント数（棒 or エリア）
  - バトル発生区間（背景に帯でハイライト）
  - スクショ撮影ポイント（マーカー。クリックで画像プレビュー）
- この1枚で「バトルで視聴者が増えた」「ギフト集中とコメント盛り上がりが同時に起きた」といった相関が視覚的に分かる
- 時間帯をクリック/範囲選択すると、その時間のコメント・ギフトに絞り込める（ドリルダウン）

### 2-4. 課題軸ビュー（①同接 ②新規ギフター ③パワーギフター）
運営チームの分析観点である3つの課題軸ごとに、関連数値をまとめたパネル。
- **①同時接続**: 視聴者数推移・ピーク・離脱タイミング・タップスルー関連
- **②新規ギフター**: 新規からのギフト・フォロー・入室・ハートミー関連
- **③パワーギフター**: ギフトランキング上位・大口ギフターの動向・そのリスナーへの対応状況
- 各パネルに勝ちパターン基準との対比を添える

### 2-5. ランキング・集計（サマリー系）
- ギフトユーザーランキング（ユーザー名・ギフレベ・ダイヤ合計）
- 入室管理（ユーザー名・ギフレベ・入室回数）
- フォロー一覧
- バトル相手一覧

## 3. L3: 詳細データ（生に近いデータ）

L2から深掘りしたい時に開く。現行のタブUIを踏襲しつつ整理。
- コメント全文（時刻・ユーザー・ギフレベ・メンバーレベル・本文、検索・フィルタ可）
- ギフト明細（1件ずつの時系列）
- その他の生イベントデータ

---

## 4. L1: 入口（配信一覧）

- 当面は「1人の配信をじっくり」が主眼なので、まずは配信一覧をシンプルに（日付・配信時間・主要KPIを一覧、選ぶとL2へ）
- 将来の複数ライバー対応（Phase 6の複数配信比較）に備え、ライバーで絞り込める余地だけ設計に残す

---

## 5. デザイン方針

- **本人と運営チーム両方が見る**前提。数値の羅列ではなく、KPIカード＋基準対比バッジで「良し悪し」が直感的に分かる見せ方を優先
- 情報の階層を明確に（上=要約・示唆 / 下=生データ）。スクロールするほど詳細になる
- 過去の類似ツール（ダークテーマの数値ダッシュボード）の見やすさは踏襲しつつ、KPIの意味づけ（基準対比）を足すのが今回の進化点
- グラフはインタラクティブに（表示切替・範囲選択・ドリルダウン）。「じっくり分析」に必要な操作性を確保

---

## 6. 実装の進め方（Phase 5前の検証と並行）

1. まずL2（1配信の分析画面）のメイン複合グラフと、KPIカード＋基準対比バッジを実装
2. 次にAIレポート表示の作り込み、課題軸ビュー
3. L3（詳細データ）は現行タブを整理して流用
4. L1（入口）は最小限から始め、複数ライバー対応は将来

各ステップで実データ（実際に記録した本番配信）を使って見え方を確認する。

---

## 7. 補足: この設計と「実運用検証」の関係

UIの作り込みは、Phase 5（複数同時監視）前の検証期間と並行して進めるのが効率的。理由:
- 実際に本番配信を通しで記録すると、L2のグラフに「長時間配信ならではの見え方の問題」（データ点が多すぎて見にくい等）が出る。これはUIを作りながらでないと分からない
- 検証で貯めた実データが、そのままUIの表示テストデータになる
