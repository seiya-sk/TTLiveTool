# Phase 5 実測プログラム仕様 — 1IPの限界を包括的に測る
## 〜 空間軸(同時何本)と時間軸(継続でいつ除外)を1本の実測で兼ねる 〜

## 目的

**1つのプロキシIPで、TikTokライブを同時に何本まで・どれくらいの時間、ブロックされずに記録し続けられるか**を、包括的に測定する。この実測で得た「1IPあたりの安全本数」「継続耐性」が、Phase 5本番の必要IP数・サーバー数を計算する土台になる。

- 使用IP: 現在のPrivateProxy.meお試しIP(1個)。追加費用を抑える
- 運転時間: 1日〜3日以上の連続運転
- 測定対象: ①同時本数の限界(空間軸)②継続時間の限界(時間軸)③サーバー負荷 ④署名消費ペース

## 測定したい4つのデータ

### 1. 空間軸: 1IPで同時何本まで安全か
- 同時接続本数を段階的に増やし、ブロック・切断・エラーが出る本数を特定する
- 「同時◯本までは安定、◯本を超えると異常」という閾値

### 2. 時間軸: 継続使用でいつ除外されるか
- 安全な本数で長時間(数日)接続し続け、いつ・どう除外されるかを観察
- 「◯時間/◯日連続で問題なし」または「◯時間目にブロックされた」

### 3. サーバー負荷: 1サーバーで何本捌けるか
- 同時本数ごとの CPU・メモリ・ネットワーク使用量
- 「同時◯本で CPU◯%・メモリ◯MB」→ 1サーバーの限界の判断材料

### 4. 署名消費ペース: Euler Streamの上限に当たるか
- RateLimit-Remaining(残署名数)の推移
- 「同時◯本で、1時間に署名◯回消費」→ 本番の署名プラン選定材料

## プログラムの動作設計

### A. ライバープールと本数維持(方法A)
- ユーザーが用意した数十人のライバーリストを「プール」として登録
- プログラムは、プールの中から**現在配信中の人**を検出し、記録対象にする
- **目標同時本数**を設定し、配信中の人でその本数を埋める
- 誰かの配信が終わったら、プールの別の配信中の人に差し替えて、本数を維持する
- 「今、実際に何本記録しているか」を常に記録する(目標本数に届かない時間帯も、それ自体がデータ)

### B. 段階的な本数増加(空間軸の測定)
- 開始時は少ない目標本数(例: 3本)から始める
- 一定時間(例: 2〜3時間)安定したら、目標本数を上げる(3→5→10→15→20...)
- 各段階で異常が出たら、その本数を記録し、一段下げて安定を確認する
- **注意**: 配信の実数がそもそも目標に届かない時間帯(昼間など)は、届く範囲で測る。夜間に本数が増やせる

### C. 異常検知と記録
- 以下を「異常」として検知・記録する:
  - 接続の切断(WebSocketが切れる)
  - 接続エラー(接続できない)
  - データ停止(接続はあるがイベントが来なくなる)
  - 署名エラー(SignatureRateLimitError) ← TikTokブロックと区別
- 各異常について「発生時刻・その時の同時本数・接続経過時間・異常の種類」を記録
- **TikTokブロックか署名上限かを区別**(前に実装したログ区別を活用)

### D. メトリクスの定期記録(例: 1分ごと)
- タイムスタンプ
- 現在の同時記録本数
- CPU使用率・メモリ使用量(サーバー負荷)
- 署名の残数(RateLimit-Remaining)
- 累計異常回数
- → これを時系列でファイル(CSV等)に記録し、後で分析できるようにする

### E. 長時間の無人運転への耐性
- 1本のライブが落ちても、全体は継続する(1つの異常で全体が止まらない)
- プログラム自体がクラッシュしても、再起動で続きから測定を再開できるとなお良い(最低限、それまでのデータは保全)
- 定期的にログ・メトリクスをファイルに書き出す(プロセスが落ちてもデータが残る)

### F. 結果の集計出力
- 実測終了後(または途中でも)、以下をまとめて出力:
  - 到達した最大同時本数と、その時の安定性
  - 異常が出た本数・時刻・種類の一覧
  - 同時本数ごとの CPU・メモリのピーク
  - 署名消費ペース(本数あたりの消費量)
  - 総運転時間、総異常回数
  - 「1IPで安全だったのは同時◯本まで、◯時間連続で問題なし」という結論

## 重要な設計上の注意

### データの保全を最優先
数日回すプログラムなので、**測定データが失われるのが最悪**。メトリクスは頻繁にファイルに書き出し、プロセスが落ちても、それまでのデータは必ず残る設計にする。「3日回したのにデータが無い」を絶対に避ける。

### 実測が「記録本体」と干渉しないこと
このプログラムは、既存の記録ロジック(client.py等)を使うが、**実測用の制御レイヤーを上に乗せる**形にする。既存の記録機能(コメント・ギフト・宝箱等の取得)を壊さない。実測で記録したデータは、通常のDBに入ってよい(後で消せる)が、実測用と分かるようにしておく。

### 倫理境界の維持(第1層)
- テスト対象は、公開されている配信のみ(ログイン不要で見られるもの)
- プロキシによるIP分散は、これまで通り第1層の範囲内
- 「配信中の人を検出する」のは、既存のcheck_is_live(公開情報での配信確認)を使う。新たにログインや非公開情報へのアクセスはしない

### プロキシIPの有効期限に注意
現在のお試しIPの有効期限(2日間)を確認すること。数日回すなら、お試し期間を延長するか、実測用に1個購入する必要があるかもしれない。**「IPの期限切れで実測が途中で止まる」を避ける**ため、開始前に期限を確認。

## 実測の進め方(運用)

1. **プログラム完成後、まず短時間(数十分)の動作確認**。段階的な本数増加・メトリクス記録・異常検知が正しく動くか、小規模で確かめる
2. 問題なければ、**本番の長時間運転(1〜3日)を開始**
3. 運転中は、定期的にメトリクスファイルを覗いて、異常が出ていないか・本数がどこまで伸びたかを確認できる
4. 運転終了後、集計出力を見て「1IPで何本・何時間」を確定
5. この数字を、Phase 5設計書の試算表に入れて、本番の必要IP数を計算する

## このプログラムが本番の土台になる

「配信中の人で目標本数を維持する」ロジックは、本番の**複数ライバー同時監視の中核**でもある。この実測プログラムで作るものは、使い捨てではなく、本番のwatch.py拡張(複数同時記録)の原型になる。実測とプロダクション設計が、ここで繋がる。
